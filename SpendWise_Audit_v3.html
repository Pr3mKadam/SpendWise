Remaining security gaps (4 items)

CRITICALMFA recovery codes stored in localStorage — bypasses MFA entirely under XSS
useAuth.tsx:145: recovery codes read/written from localStorage.getItem('sw_recovery_codes'). A recovery code is a full MFA bypass. Storing it in the most XSS-accessible browser store means any script injection can silently extract the recovery code and then bypass the MFA it was meant to protect. Move to encrypted IndexedDB, or better, never store locally — display once and discard.
HIGHShared wallet P2P still on public MQTT brokers — financial data unencrypted in transit
Despite the comment saying "REPLACES PeerJS with Supabase Realtime," syncEngine.ts still uses @trystero-p2p/mqtt connecting to wss://broker.hivemq.com — a fully public broker. Anyone with a groupId can join and receive all real-time financial mutations. The fix (move to Supabase Realtime) is stated in the file's own header but not implemented.
HIGHSupabase auth tokens still in localStorage — not migrated to custom adapter
The Supabase client is not configured with a custom storage adapter. Supabase defaults to localStorage for session persistence, meaning access and refresh tokens remain in the most XSS-accessible store. The ROADMAP has flagged this for 3 builds. The fix is one line in the Supabase client config: auth: { storage: sessionStorage }.
MEDIUMReactMarkdown in ReportsView renders unsanitised Gemini output
ROADMAP flags this since v1: "Sanitize Gemini markdown output in ReportsView.tsx." rehype-sanitize is not installed. If the Gemini proxy is ever compromised or returns malicious output, it will be rendered into the DOM. One dependency + one prop to fix.
